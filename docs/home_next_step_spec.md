# ホーム「次の一歩」設計

更新日：2026年9月13日

## As-Is / To-Be

| 観点 | As-Is | To-Be |
|---|---|---|
| 案内 | 全利用者に固定の「基本情報を入力する」 | 本人の保存状態・応募予定から1件を選ぶ |
| 更新 | 行動と無関係 | ホーム表示時にDBから再判定。古い判定をキャッシュしない |
| 表示 | アイコン・見出し・説明2行・ボタン | 構成・CSSを維持。説明とボタンの文言・移動先を変更 |
| 処理 | 固定HTML | 決定ルール。AI呼出しやデータ更新は行わない |

## 優先順

1. 進行中応募の未完了予定：期限超過・当日・7日以内。古い予定から優先。同日なら応募ID・予定ID順で安定させる。会社・予定名・日付を示し、その応募の管理画面へ移動。
2. 基本情報／希望条件／価値観／就活の軸の一時保存：最新の下書きを再開。正式保存後でも編集の下書きが残っていれば再開を案内。
3. 進行中の応募：応募準備を優先し、同条件なら応募ID順。結果待ちは「結果が届いたら記録」と案内する。
4. 応募の意思決定済みで応募管理に未登録の求人：「応募する」「他経路から応募する」「条件を確認して応募」を対象に、求人一覧から条件・経路を確認する。
5. 自己理解の保存不足：基本情報→希望条件→価値観→就活の軸→職務経歴・スキルの順で確認・入力へ。
6. 求人が0件：求人登録へ。
7. 未判断・保留・条件確認の求人がある：求人一覧へ。
8. 求人の判断済みで応募履歴がある：活動の振り返りへ。それ以外は次の求人登録へ。

## 判定する保存情報

- 基本情報：削除されていないプロフィールと主要項目の保存。
- 希望条件：年収の保存と職種・勤務地・雇用形態の登録。
- 価値観：3グループそれぞれ順位1～3の登録と、仕事の進め方の全設問に1～5の回答があること。
- 就活の軸：名称と判断基準のある正式保存データが1件以上。
- 職務経歴：会社名のある正式保存データが1件以上。

これはホームの案内用の保存状況判定であり、各フォームの全検証や必須項目の仕様を置き換えない。職歴のない人のスキップ判定や、ブラウザ上だけの未保存入力の推測は今回追加しない。

## データアクセス・更新

`home_progress_repository.get_home_progress`は本人IDの権限確認後、固定の集計SQL1回と下書き一覧SQL1回で必要な情報を取得する（利用停止確認のSQLは別）。求人の応募判断は求人所有者と判断所有者を両方一致させる。削除済み情報は除外する。既存の期限タスク表示で取得する応募一覧を再利用し、応募一覧の二重読込を避ける。

`home_next_step_service.choose_next_step`はDBから独立した純粋な判定処理。日付は日本時間。完了・延期・中止予定、終了応募、不正日付は期限案内から除外する。会社名などの表示値はHTMLエスケープする。クリック時の遷移先でも既存の所有者チェックを維持。

ホームに戻る／ホームが再実行される時点の保存情報を使用する。開きっぱなしのホームへ別端末の更新を即時配信する機能や自動ポーリングは追加しない。

## 検証

新規利用・基本情報保存後・価値観不足・下書き再開・期限優先・期限7日境界・完了等の除外・不正日付・応募中・求人判断・振り返り・HTMLエスケープを検証。実SQLiteで利用者2人、下書き分離、他人ID拒否、判断変更、求人削除を確認（新規テスト10件）。実PostgreSQLにも読み取りのみで接続し、集計SQLと判定が実行できることを確認。公開環境の表示はデプロイ後に記録する。
