# MeTeA AIマッチング仕様

## 1. 目的

MeTeAのAIマッチングは、利用者に「応募すべき求人」を決める機能ではない。

最新の利用者情報と求人情報を比較し、

「現在の自分と、この求人がどの程度合っているのか」

を整理して、利用者自身の応募判断を支援することを目的とする。

AIは意思決定を代替せず、以下を提示する。

- 総合適合度
- 合っている点
- 懸念点
- 次に確認すること
- 評価理由

最終的な応募判断は利用者自身が行う。


## 2. 基本原則

1. AIが評価するのは応募推奨度ではなく適合度とする。
2. 最新の利用者情報と求人情報を使用する。
3. 情報不足は不一致ではなく「要確認」とする。
4. 根拠が弱い場合は無理に一致判定しない。
5. 求人側の必須条件に不一致があっても自動除外しない。
6. 過去の職種・業種が異なるだけで低評価にしない。
7. AI評価と利用者の応募判断を分離する。
8. 評価根拠を利用者が確認できるようにする。
9. 数値や選択肢で判定できる項目はルールで判定する。
10. AIに総合点を自由に決めさせない。


## 3. AIおすすめ求人の定義

求人一覧画面の「AIおすすめ求人TOP3」は、登録済み求人のうち、現在の利用者情報との総合適合度が高い上位3件とする。

AIおすすめは応募推奨を意味しない。

求人一覧の「AIおすすめ順」とTOP3は、同一の評価結果を使用する。


## 4. 評価に使用する情報

### 4-1. 利用者情報

- 基本情報
- 現在の最寄駅

- 希望条件の優先度
- 価値観と順位
- 就職活動の軸と順位
- 職務経歴
- 担当業務
- 実績
- スキル
- 強み
- ポータブルスキル

### 4-2. 求人情報

- 基本情報
- 仕事内容
- 応募資格
- 求人側の必須要件
- 歓迎要件
- 勤務地
- 勤務地の最寄駅
- 給与・待遇
- 雇用形態
- 勤務時間
- 残業時間
- 休日
- 年間休日
- 転勤
- 働き方
- 福利厚生
- 選考情報


## 5. 「必須」という言葉の区別

本仕様では「必須」を次の2種類に分ける。

### 5-1. 利用者設定の優先度「必須」

利用者が希望条件に設定する重要度である。

例：

- 転勤条件を必須にする
- 雇用形態を必須にする
- 勤務地を必須にする

利用者設定の優先度は、希望条件40点の内部計算に使用する。

求人側の応募必須条件10点には含めない。

利用者優先度の「必須」が不一致でも、それだけを理由に求人を自動除外しない。

### 5-2. 求人側の応募必須条件

企業が応募資格として必須と明示している条件である。

例：

- 普通自動車免許必須
- 資格必須
- 実務経験3年以上必須
- 特定ツールの実務経験必須

求人側の応募必須条件は、必須条件評価10点で判定する。

### 5-3. 両者の関係

利用者設定の「必須」と、求人側の「応募必須条件」は別概念として扱う。

点数枠、減点処理、表示上の状態を共有しない。

画面や内部処理では、可能な限り次の名称を使用する。

- 利用者優先度：必須
- 求人側応募必須条件


## 6. 総合適合度

総合適合度は次の4項目から算出する。

| 評価項目 | 配点 |
|---|---:|
| 希望条件 | 30点 |
| 確定した就職活動の軸 | 35点 |
| 職務経歴・ポータブルスキル | 25点 |
| 求人側応募必須条件 | 10点 |
| 合計 | 100点 |


## 7. 判定ラベル

各評価項目は次の4段階で判定する。

| 判定 | 計算用得点 |
|---|---:|
| 一致 | 100 |
| 一部一致 | 60 |
| 不一致 | 0 |
| 要確認 | 計算対象外 |

「要確認」は0点として扱わない。

要確認項目は、点数計算の分子と分母の両方から除外し、「次に確認すること」へ表示する。


## 8. 利用者優先度

希望条件では次の優先度を使用する。

| 優先度 | 重み |
|---|---:|
| 必須 | 3 |
| 希望 | 2 |
| 許容 | 1 |
| こだわらない | 0 |

「こだわらない」は評価対象外とする。

利用者優先度の「必須」は、求人側応募必須条件10点には含めない。


### 8-1. 企業業種の「こだわらない」

企業業種で「こだわらない」を選択した場合、業種はAIマッチングの評価対象外とする。

求人の業種が未入力または利用者の経験業種と異なる場合も、業種だけを理由に減点しない。


### 8-2. キャリア・組織風土の否定条件

キャリア・組織風土では、通常の優先度に加えて次の選択肢を使用する。

| 選択肢 | 意味 | 評価方向 | 重み |
|---|---|---|---:|
| 希望しない | できれば避けたい条件 | 求人に該当する場合は不一致寄り | 2 |
| 不可 | 受け入れられない条件 | 求人に該当する場合は強い不一致 | 3 |

「希望しない」と「不可」は、求人にその要素があることを望む条件ではない。
AIは正方向の希望と混同せず、求人に該当要素がある場合をマイナス方向に判定する。
求人票から該当の有無を確認できない場合は「要確認」とする。


## 9. 確定した就職活動の軸の順位

| 順位 | 重み |
|---|---:|
| 1位 | 3 |
| 2位 | 2 |
| 3位 | 1 |

順位が高い項目ほど、カテゴリスコアへの影響を大きくする。


## 10. カテゴリスコアの計算

カテゴリ一致率は次の式で計算する。

カテゴリ一致率<br>
＝ Σ（判定得点 × 重み）<br>
÷ Σ（採点可能な項目の重み）

「要確認」と「こだわらない」は、分子と分母から除外する。

カテゴリ内のすべての項目が要確認の場合、そのカテゴリ自体を要確認とする。

総合点計算では、採点可能なカテゴリだけを使用し、残りのカテゴリ配点を100点満点へ再配分する。


### 10-1. 評価カバー率と暫定評価

採点可能なカテゴリが全体のどの程度を占めるかを示すため、評価カバー率を算出する。

評価カバー率<br>
＝ Σ（採点可能なカテゴリの本来の配点）<br>
÷ 100点<br>
× 100

例として、職務経歴・ポータブルスキル25点だけが採点可能な場合、評価カバー率は25%となる。

採点可能なカテゴリだけで再配分した総合適合度が100点であっても、評価カバー率が100%未満の場合は「暫定評価」として表示する。

画面では、単に「100点」と表示せず、次の情報を併記する。

- 暫定評価であること
- 再配分後の総合適合度
- 評価できた情報の割合
- 未評価または要確認のカテゴリ

表示例：

```text
暫定AI総合マッチ度：100点
評価できた情報：25%


## 11. 希望条件40点の内部構成

| カテゴリ | 比重 |
|---|---:|
| 勤務地・転勤 | 25% |
| 年収・雇用条件 | 25% |
| 勤務時間・休日 | 25% |
| 働き方・職場環境 | 15% |
| その他条件 | 10% |


## 12. 年収判定

求人票に年収範囲がある場合は、原則として保証される下限額を使用する。

| 求人年収 | 判定 |
|---|---|
| 最低許容年収未満 | 不一致 |
| 最低許容年収以上、希望年収未満 | 一部一致 |
| 希望年収以上 | 一致 |
| 理想年収以上 | 一致＋上振れ表示 |
| 金額不明・応相談 | 要確認 |

理想年収を上回っても100点を超える加点はしない。

最低許容年収は利用者の希望条件であり、求人側応募必須条件10点には含めない。


## 13. 電車移動時間判定

### 13-1. 定義

一般的なドア・ツー・ドアの通勤時間ではなく、次の時間を評価する。

「利用者の現在の最寄駅から、勤務地の最寄駅までの片道の電車移動時間」

自宅から現在の最寄駅までの徒歩時間と、勤務地の最寄駅から勤務先までの徒歩時間は含めない。

画面上では「通勤時間」ではなく「電車移動時間」と表示する。


### 13-2. 必要な情報

利用者情報には次を登録する。

- 現在の最寄駅
- 現在の最寄駅の識別情報

求人情報には、求人票に記載されている場合だけ次を登録する。

- 勤務地の最寄駅

求人票に記載されていない勤務地の最寄駅を、利用者に推測して入力させない。

電車移動時間は求人そのものの情報ではなく、「利用者と求人の組み合わせごとの確認情報」として管理する。

確認情報には次を保存する。

- 利用者ID
- 求人ID
- 出発駅
- 到着駅
- 片道の電車移動時間
- 確認日
- 取得元


### 13-3. 暫定実装

プロダクト全体が完成するまでの暫定対応として、外部の経路計算APIによる自動算出は行わない。

求人確認画面のAIマッチング結果より下に「要確認：通勤時間」を表示する。

求人票に勤務地の最寄駅が記載されている場合は、利用者がGoogleマップなどで次の条件を確認し、片道の電車移動時間を入力できる。

- 出発地は利用者の現在の最寄駅
- 到着地は求人票に記載された勤務地の最寄駅
- 通常利用する経路
- 乗り換え時間を含む
- 徒歩時間を含まない

同じ駅の場合は0分を入力できる。

電車移動時間は求人登録画面や求人編集画面へ入力しない。

求人票に勤務地の最寄駅が記載されていない場合は、入力欄を表示せず「要確認」とする。


### 13-4. 判定

| 電車移動時間 | 判定 |
|---|---|
| 利用者の上限以内 | 一致 |
| 上限＋1～5分 | 一致。ただし「上限に近い」と表示 |
| 上限＋6分以上 | 不一致 |
| 未確認 | 要確認 |
| 求人票に最寄駅の記載なし | 要確認 |

「要確認」は0点や不一致として扱わない。


### 13-5. 電車移動時間が確認できない場合

次の場合は、電車移動時間を「要確認」とする。

- 求人票に勤務地の最寄駅が記載されていない
- 利用者が電車移動時間をまだ確認していない
- 出発駅または到着駅を特定できない

要確認の場合は、電車移動時間を点数計算の分子と分母から除外する。

電車移動時間が未確認であることだけを理由に、AI評価全体を停止しない。

電車移動時間が未確認であることだけを理由に、総合点を減点しない。

画面の「次に確認すること」に、通勤時間の確認が必要であることを表示する。


### 13-6. 駅すぱあとによる自動算出予定

プロダクト全体の主要機能が完成した後、直近の追加開発として「駅すぱあと API」を利用した電車移動時間の自動算出を実装する。

自動算出では、次の情報を使用する。

- 利用者の現在の最寄駅
- 求人票に記載された勤務地の最寄駅
- 駅すぱあと APIが返す公共交通機関の経路
- 乗り換え時間を含む片道の所要時間

駅すぱあと API導入前に、次を確認する。

- 利用プラン
- 月額費用またはリクエスト料金
- 利用上限
- 対象地域
- 本番利用条件
- アクセスキーの管理方法
- 求人サービスでの利用条件
- キャッシュおよび保存に関する利用規約

自動算出を導入した後も、API障害や経路を取得できない場合に備えて、手動確認を代替手段として残す。

経路計算サービス固有の処理は、AI評価処理や画面へ直接記述しない。

次の共通形式で電車移動時間を受け渡す。

```python
duration_minutes: int
source_type: str
checked_at: str
```

`source_type` は次のいずれかとする。

- `manual`
- `ekispert_api`

手動確認と自動算出では、同じ電車移動時間判定ルールを使用する。


### 13-7. 実装優先順位

実装順序は次のとおりとする。

1. プロダクト全体の主要画面と主要機能を完成させる
2. AIマッチングの基本ロジックを完成させる
3. 暫定的な手動確認方式で全体動作を検証する
4. 駅すぱあと APIの契約・料金・利用条件を確定する
5. 電車移動時間の自動算出を実装する
6. 手動確認方式をフォールバックとして残す

駅すぱあと API対応は廃止予定の機能ではなく、プロダクト全体完成後に優先して実装する直近の開発項目として管理する。


## 14. 残業時間

| 求人内容 | 判定 |
|---|---|
| 利用者の上限以内 | 一致 |
| 利用者の上限超過 | 不一致 |
| 「月10～30時間」など幅がある | 要確認 |
| 数値不明 | 要確認 |


## 15. 始業・終業時刻

利用者が「9時以降」を希望し、求人が9時以降開始の場合は一致とする。

求人の始業時刻が希望より早い場合は不一致とする。

利用者が「18時まで」を希望し、求人が18時までに終了する場合は一致とする。

求人の終業時刻が希望より遅い場合は不一致とする。

フレックスタイム制でコアタイムなどが不明な場合は要確認とする。


## 16. シフト勤務・夜勤

| 利用者設定と求人内容 | 判定 |
|---|---|
| 不可／求人にシフト・夜勤あり | 不一致 |
| 条件次第で可／求人にシフト・夜勤あり | 要確認 |
| 可 | 不一致にしない |
| 求人情報に記載なし | 要確認 |
| こだわらない | 評価対象外 |


## 17. 年間休日

| 求人内容 | 判定 |
|---|---|
| 希望年間休日数以上 | 一致 |
| 希望年間休日数未満 | 不一致 |
| 年間休日数不明 | 要確認 |

希望値を少し下回る場合でも、一部一致にはしない。


## 18. 休日形態

休日形態は休日数ではなく、利用者が指定した休日パターンとの一致で判定する。

| 求人内容 | 判定 |
|---|---|
| 希望する休日パターンを満たす | 一致 |
| 希望と異なる固定休日 | 不一致 |
| シフト調整などで実現できる可能性がある | 要確認 |
| 記載が曖昧 | 要確認 |

休日形態では、原則として「一部一致」を使用しない。

例：

利用者が土日祝休みを希望し、求人が土曜日のみ固定休の場合は不一致とする。


## 19. 転勤条件

利用者が「条件次第で可」、求人が「転勤あり」の場合は要確認とする。

次の情報を確認事項として表示する。

- 転勤範囲
- 頻度
- エリア
- 本人同意の有無
- 適用条件

情報不足の状態で一部一致にはしない。


## 20. 勤務地

| 求人内容 | 判定 |
|---|---|
| 希望する都道府県・市区町村と一致 | 一致 |
| 都道府県は一致し、市区町村が異なる | 一部一致 |
| 利用者優先度が必須の都道府県と異なる | 不一致 |
| 勤務地未定・複数候補 | 要確認 |
| 利用者が勤務地を設定していない | 評価対象外 |

隣接地域や通勤可能性を、根拠なく推測しない。


## 21. 雇用形態

| 求人内容 | 判定 |
|---|---|
| 希望する雇用形態と一致 | 一致 |
| 複数希望のうち許容可能な形態 | 一部一致 |
| 希望対象外 | 不一致 |
| 求人側の記載なし | 要確認 |


## 22. その他の希望・NG条件

自由記述はAIが意味を解析する。

「絶対に」「不可」「NG」「避けたい」などは、利用者優先度の「必須」に相当する強い希望として扱う。

求人側応募必須条件には含めない。

「できれば」「希望」「あると嬉しい」などは、利用者優先度の「希望」に相当するものとして扱う。

重要度を判断できない場合は要確認とする。


## 23. 価値観と就職活動の軸

### 23-1. 価値観の役割

価値観、やりがいを感じる場面、力を発揮しやすい環境、仕事の進め方は、就職活動の軸候補を作成する材料として使用する。

価値観の生回答は、AI総合適合度の独立した採点対象にしない。

### 23-2. 軸候補の作成と確定

希望条件と価値観を保存した後、アプリは最大3件の就職活動の軸候補を作成する。

候補生成は初期リリースではPythonルールで行い、外部AI APIは呼び出さない。

候補には、軸の名称と具体的な判断基準を含める。利用者は候補を編集、削除、追加、並び替えできる。

候補は自動確定しない。利用者が画面で確認し、「この内容で確定して次へ」を実行した内容だけをAIマッチングへ使用する。

既に確定済みの軸がある場合は、価値観を再入力しても自動上書きしない。

利用者が「入力内容から軸候補を作り直す」を明示的に選び、確認操作を行った場合に限り、画面上の軸を最新の希望条件と価値観から作成した未確定候補へ置き換える。置き換え後も、利用者が確定操作を行うまでは正式保存しない。

### 23-3. AIマッチングでの評価

AIは、確定した軸と求人票に記載された次の情報を比較する。

- 仕事内容
- 役割
- 制度
- 働き方
- キャリア形成機会

軸カテゴリの配点は35点とし、総合適合度で最も大きい配点とする。

軸の順位は、1位を重み3、2位を重み2、3位を重み1としてカテゴリスコアへ反映する。

価値観と確定軸を重複して採点しない。

企業文化、人間関係、実際の裁量、実際の働きやすさなど、求人票から判断できない事項は要確認とする。根拠が弱い状態で一致や一部一致にしない。

## 24. 職務経歴・ポータブルスキル

職種名・業種名の一致は補助情報として扱う。

評価は次の順序で行う。

1. 求人側応募必須条件の確認
2. 利用者の経験と実績の確認
3. ポータブルスキルの抽出
4. 求人業務との接続の評価
5. 職種名・業種名の関連性を補助情報として参照

主なポータブルスキルは次のとおり。

- 課題発見
- 関係者調整
- 顧客対応
- 業務改善
- 企画
- マネジメント
- 数値管理
- 文章作成
- 情報整理
- プロジェクト推進

過去職種が求人職種と異なるだけでは減点しない。

ポータブルスキルを評価する場合は、次の3点を関連付けて説明する。

1. ポータブルスキル
2. 根拠となる過去の経験
3. 求人でどのように活かせるか


## 25. 求人側応募必須条件

求人側が必須と明示する資格、免許、経験、専門スキルを評価する。

| 利用者の状態 | 判定 |
|---|---|
| 保有・経験が確認できる | 一致 |
| 要件の一部を満たしている | 一部一致 |
| 保有していないことが明確 | 不一致 |
| 利用者情報に記載がなく判断できない | 要確認 |

プロフィールに書かれていないだけで、不足と断定しない。

ポータブルスキルによって、必須資格や必須経験を満たしたことにはしない。


## 26. 求人側重大必須条件の減点

求人側の重大な応募必須条件について、明確な不一致がある場合は追加減点する。

初期値は次のとおりとする。

```python
MAJOR_REQUIRED_CONDITION_PENALTY = 20
MAX_REQUIRED_CONDITION_PENALTY = 40
```

減点ルールは次のとおりとする。

- 重大な不一致1件につき20点減点
- 減点上限は40点
- 要確認では減点しない
- 利用者優先度の「必須」には適用しない
- 総合点は0点未満にしない
- 減点値はコード内へ直接記載せず、定数として管理する


## 27. AIとルール判定の役割

次の項目はPythonのルールで判定する。

- 年収
- 手動入力された電車移動時間
- 残業時間
- 始業・終業時刻
- 年間休日数
- 転勤条件
- 雇用形態
- 明確な資格保有状況

電車移動時間が未確認の場合は、AIに推測させない。

利用者が通勤時間を評価対象にしていても、電車移動時間が未確認の場合は「要確認」とする。

要確認の電車移動時間は点数計算から除外し、未確認であることだけを理由にAI評価全体を停止または減点しない。

次の項目はAIによる意味判定を使用する。

- 価値観
- 就職活動の軸
- その他の希望・NG条件
- 職務経歴
- ポータブルスキル
- 求人業務との接続
- 求人票内の必須要件の抽出

AIは総合点を直接決定しない。

AIは項目ごとに次のいずれかを返す。

- 一致
- 一部一致
- 不一致
- 要確認

アプリ側がAIの構造化結果とルール判定結果を使用して点数を計算する。

## 29. AIコメント

### 合っている点

利用者情報と求人情報の双方に根拠があり、一致を確認できる内容を表示する。

### 懸念点

利用者情報と求人情報の明確な不一致を表示する。

情報不足は懸念点に含めない。

### 次に確認すること

情報不足によって要確認と判定した内容を表示する。

### 評価理由

利用者情報と求人情報のどの部分を根拠にしたか分かるように表示する。


## 30. AIに禁止すること

AIは次のことを行わない。

- 応募すべきかどうかを最終判断する
- 求人票にない企業文化を事実として断定する
- 情報不足を不一致として扱う
- 根拠が弱いものを無理に一部一致にする
- 職種・業種の違いだけで低評価にする
- 必須条件不一致だけを理由に求人を自動除外する
- 根拠のないポータブルスキルを生成する
- 利用者情報や求人情報にない事実を補完する
- 電車移動時間を推測する
- 総合点を自由に決める
- 利用者優先度の必須と求人側応募必須条件を混同する


## 31. 評価処理順序

1. 最新の利用者情報と求人情報を取得する
2. 入力情報が評価可能か確認する
3. 電車移動時間などの確認状況を判定する
4. ルール判定項目を評価する
5. AIによる意味判定を実行する
6. カテゴリスコアを算出する
7. 求人側重大必須条件の減点を適用する
8. コメントと評価理由を生成する
9. 構造化した評価結果を返す
10. 有効なキャッシュを保存する

電車移動時間が未確認の場合も、AI評価のほかの項目は処理する。

未確認の電車移動時間は点数計算から除外し、画面の「次に確認すること」へ表示する。

電車移動時間は求人編集画面ではなく、求人確認画面で利用者と求人の組み合わせごとに確認する。


## 32. 保存とキャッシュ

AI評価は利用者の正式な判断データとして固定保存しない。

API負荷と表示速度のため、評価結果をキャッシュとして保存できる。

キャッシュには最低限、次を保存する。

- 利用者ID
- 求人ID
- 入力情報のハッシュ値
- 評価ルールのバージョン
- AIプロンプトのバージョン
- 使用モデル
- 評価日時
- 評価結果JSON

次のいずれかが変わった場合、以前のキャッシュを無効にする。

- 基本情報
- 現在の最寄駅
- 希望条件
- 価値観
- 就職活動の軸
- 職務経歴・スキル
- 求人情報
- 求人の最寄駅
- 電車移動時間、対象駅、取得元など、通勤時間評価へ影響する情報
電車移動時間の確認日だけが更新され、分数、対象駅および取得元が変わっていない場合は、評価結果へ影響しないため再評価しない。
- 評価ルール
- AIプロンプト
- 使用AIモデル

AI評価キャッシュと、利用者が保存した応募判断は別データとして管理する。


### 32-1. AI評価キャッシュの状態管理

保存済みのAI評価には、少なくとも次の状態を保持する。

- 再評価待ちかどうか
- 再評価待ちになった理由
- 評価カバー率
- 暫定評価かどうか

利用者情報または求人情報が変更された場合、保存済み評価の点数や評価理由を直ちに削除しない。

既存評価へ再評価待ちの状態と理由を設定し、新しい評価が正常に保存されるまで古い評価と区別して保持する。

利用者情報では、次の正式保存内容が実際に変わった場合に、現在の利用者に紐づく求人評価を再評価待ちにする。

- 基本情報
- 希望条件
- 価値観
- 就職活動の軸
- 職務経歴・スキル

入力途中の下書き保存では、AI評価キャッシュを無効化しない。

正式保存操作を行っても、保存前後の内容が同一の場合はAI評価キャッシュを無効化しない。


### 32-2. AI評価の実行タイミング

AI評価は、利用者が都度実行ボタンを押す方式にはしない。

次の場合に、システムがAI評価を自動実行する。

- 求人を新規登録した場合
- 求人情報を編集して保存した場合
- 類似求人を別求人として新規登録した場合
- 利用者情報の変更により、既存評価キャッシュが再評価待ちになった場合
- 求人確認画面で電車移動時間を初回保存または変更した場合

電車移動時間を初回保存または変更した場合は、対象求人1件だけを再評価待ちにし、その求人を自動再評価する。

保存前後の電車移動時間が同一の場合は、AI評価を再実行しない。

求人の紹介経路を追加しただけで、評価対象となる求人内容が変わっていない場合は再評価しない。

有効な評価キャッシュが存在する場合、求人一覧、求人確認画面、比較結果画面を表示しただけではAI評価を再実行しない。

再評価待ちの求人が存在する状態で求人一覧を表示した場合は、システムが再評価を自動実行する。

APIリクエストの集中、画面の長時間停止および意図しない費用増加を防ぐため、求人一覧の1回の処理で自動再評価する件数は最大3件とする。

3件を超える再評価待ち求人は待機状態を維持し、次の求人一覧画面の操作または再表示時に続けて処理する。

同一の再評価待ち一覧に対して、Streamlitの同一画面再実行による重複APIリクエストを発生させない。

通常の利用者向け画面には「AI評価を実行する」ボタンを設置しない。


### 32-3. AI評価失敗時の扱い

求人情報または利用者情報の保存と、AI評価の成功・失敗は分離して扱う。

求人情報や利用者情報の保存に成功した後でAI評価に失敗しても、保存済みの入力情報を取り消さない。

画面には、状況に応じて次の趣旨を表示する。

```text
入力情報は保存されましたが、AIマッチング評価を完了できませんでした。

AI評価に失敗した結果を、0点または不一致として保存しない。
既存評価がある状態で再評価に失敗した場合は、古い評価を再評価待ちとして保持する。
再評価に成功した求人だけ、新しい評価結果を保存し、再評価待ち状態を解除する。
再評価に失敗した求人は再評価待ち状態を維持し、成功した評価として画面表示や並び替えに使用しない。

## 36. 最終設計思想

MeTeAのAIマッチングは、過去と同じ仕事を探すためだけの適合判定ではない。

利用者が、これまでの経験から何を得て、何を大切にし、次の仕事で何を実現したいのかを求人情報と照らし合わせる。

AIが答えを決めるのではなく、情報を整理し、利用者自身が納得して判断できることを最優先とする。
