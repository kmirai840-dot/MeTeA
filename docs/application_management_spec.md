# MeTeA 応募後管理仕様

## 1. 目的

MeTeAの応募後管理機能は、
求人へ応募することを決めた後の活動を一元管理し、

- 現在どの選考段階にいるか
- 次に何をする必要があるか
- いつまでに対応する必要があるか
- 過去に何をしたか
- 次の選考に向けて何を準備するか

を利用者が迷わず把握できる状態を作ることを目的とする。

求人情報そのものの管理と、
応募後の活動・選考状況の管理は分離する。


# 2. 求人管理との役割分担

求人関連画面では、

- 求人登録
- 求人比較
- AIマッチング
- 求人詳細確認
- 応募判断

までを扱う。

求人確認画面で利用者が「応募する」と判断した求人は、
応募後管理へ連携する。

応募後管理では、
その後の選考状況、予定、期限、活動、選考準備を管理する。


# 3. 応募後管理の画面構成

応募後管理は、
大きく以下の3画面で構成する。

1. 応募管理画面
2. 応募詳細画面
3. 選考準備画面


## 3-1. 応募管理画面

応募管理全体の起点となる画面。

以下を同一画面内に配置する。

- 応募状況サマリー
- 対応が必要な項目
- 直近のマイルストーン
- 応募企業一覧

「応募企業一覧」と「マイルストーン」は、
相互に連動する情報であるため、
別画面へ分離せず同一の管理画面に配置する。


## 3-2. 応募詳細画面

1件の応募について、
選考状況を詳しく確認・更新する画面。

以下を扱う。

- 応募情報
- 現在の選考ステータス
- マイルストーン
- 活動履歴
- 選考準備への導線


## 3-3. 選考準備画面

従来「下書き」として想定していた機能は、
「選考準備」として扱う。

単なる文章保存ではなく、
応募・面接等に向けた準備情報を整理する機能とする。

具体的なテーマ一覧、保存単位、UIについては、
今後追加で仕様を確定する。


# 4. 応募管理への連携

求人確認画面で利用者が「応募する」と判断した求人は、
応募管理へ連携する。

応募管理へ追加された後は、
求人一覧ではなく応募管理側で選考ステータスを管理する。

求人票情報と応募・選考情報は別データとして扱う。


# 5. 応募単位

応募管理では、
単なる会社単位ではなく、

「求人 × 実際の応募経路」

を意識して管理する。

同一求人を複数の紹介経路から受け取っていても、
実際に応募した経路を応募情報として明示する。

紹介経路と応募経路は別概念として扱う。

14. マイルストーンの完了
マイルストーンは、
予定日時を過ぎただけでは自動完了しない。
利用者が明示的に「完了」とした時点で、
完了扱いとする。
面接や適性検査等の予定日時を過ぎても、
未完了の場合はステータスを勝手に更新しない。
15. 対応が必要
予定日時または期限を過ぎても、
未完了のマイルストーンが存在する場合は、
「対応が必要」
の領域へ表示する。
15-1. 対応が必要となる例
日時を過ぎた未完了の適性検査
日時を過ぎた未完了の面接
日時を過ぎた未完了の面談
提出期限を過ぎたタスク
回答期限を過ぎたタスク
選考結果等の更新が必要な状態
日時を過ぎただけで、
自動的に完了、不合格、辞退等へ変更しない。
16. 近日予定
近日予定は、
「現在日から直近1週間以内」
に存在する未完了マイルストーンとする。
17. 期限超過
期限として登録したマイルストーンは、
「期限当日になった時点」
で期限超過扱いとする。
期限超過した未完了項目は、
「対応が必要」へ表示する。

3. 応募企業一覧とマイルストーンは同一画面で確認できるようにする。
4. 予定日時を過ぎただけで選考状態を勝手に変更しない。
5. 利用者の操作によって実際の活動状態を確定する。
6. 放置された予定・期限は見逃さないよう目立たせる。
7. データ構造と画面構造を同一視しない。
8. 関連する情報はUI上でまとめ、内部データは役割ごとに分離する。
9. TOP画面では詳細ではなく、次の行動に必要な情報を優先する。
10. 利用者が迷わず選考を進められることを最優先とする。


# 29. マイルストーン入力項目

マイルストーンは、
応募後の選考・対応・期限を管理するための予定情報とする。

すべての項目を常に表示するのではなく、
選択したマイルストーン種別に応じて必要な入力欄のみ表示する。


## 29-1. 共通項目

すべてのマイルストーンは、
最低限以下の情報を持つ。

- 対象応募ID
- マイルストーン種別
- タイトル
- 予定／期限の区分
- 予定日または期限日
- 開始時刻
- 終了時刻
- 状態
- メモ

会社名、求人名、応募経路等は、
対象応募IDから取得する。

応募詳細画面からマイルストーンを登録する場合は、
利用者に会社名や求人名を再入力させない。


# 30. マイルストーン種別

- 応募
- 書類提出
- 適性検査
- カジュアル面談
- 一次面接
- 二次面接
- 最終面接

- オファー面談
- 条件面談
- 企業への回答期限
- 内定承諾期限
- その他

マイルストーン内部では、

- 予定
- 期限

- 服装

- オンライン
- 対面
- 電話
- その他

会議ID、パスコード、持ち物、服装等は任意入力とする。


# 32. 適性検査マイルストーン

適性検査では、

書類提出では、

- 提出物
- 提出期限
- 提出先
- 提出方法
- メモ

提出方法は以下を基本とする。

- Web
- メール
- エージェント経由
- その他

提出済みかどうかは、

別の状態を二重管理しない。


# 34. 回答期限系マイルストーン

企業への回答期限、

- 期限日
- 期限時刻
- 回答内容
- メモ

期限当日になった時点で、
未完了の場合は期限超過として扱い、
「対応が必要」へ表示する。

- 中止

自動的に完了へ変更しない。

利用者が明示的に完了操作を行った時点で、
完了とする。

就職活動ダッシュボードの分析に利用する構造とする。

# 45. 活動履歴の目的

活動履歴は、

「応募後に、いつ・何が起きたのか」

を時系列で確認するための記録機能とする。

単なる操作ログではなく、
選考の進行や企業・エージェントとのやり取りを
後から確認できることを目的とする。

活動履歴は応募詳細画面内に表示し、
独立した管理画面には分離しない。


# 46. 活動履歴の分類

活動履歴は、
以下の3種類に分類する。

1. 選考イベント
2. 管理上の変更
3. コミュニケーション活動


## 46-1. 選考イベント

応募・選考そのものに関する出来事。

原則としてシステムが自動記録する。


## 46-2. 管理上の変更

現在フェーズやマイルストーン等、
MeTeA上の管理状態が変化した記録。

原則としてシステムが自動記録する。


## 46-3. コミュニケーション活動

企業・採用担当者・エージェント等との
メール、電話、面談等のやり取り。

原則として利用者が手動記録する。


# 47. 活動履歴の自動記録対象

以下の出来事は、
活動履歴へ自動記録する。


## 47-1. 応募関連

- 応募管理への追加
- 応募完了
- 応募経路の確定・変更


## 47-2. 選考フェーズ関連

- 書類不合格
- 適性検査通過
- 適性検査不合格
- 各面接・面談の通過
- 各面接・面談の不合格
- 内定
- 保留
- 見送り
- 辞退
- 選考終了


## 47-3. マイルストーン関連

- マイルストーン新規登録
- 日程変更
- 延期
- 延期後の新日程登録
- 完了
- 中止


## 47-4. 実施完了イベント

- 書類提出完了
- 適性検査完了
- カジュアル面談完了

- 二次面接完了

TOP画面には直近1週間の重要活動を最大3件表示する。
過去のフェーズ変更履歴を保持する。
就職活動ダッシュボードの分析に利用する構造とする。
活動履歴を利用者の日記ではなく、選考進行を確認する記録として設計する。

# 60. 選考準備の目的

従来「下書き」として想定していた機能は、
「選考準備」として扱う。

選考準備は、
単なる文章保存機能ではなく、

「次の応募・面接・選考に向けて準備するための情報整理機能」

とする。

利用者が、

- 自分自身について整理する
- 企業ごとの志望理由を整理する
- 面接ごとの想定質問や逆質問を準備する
- AIマッチング結果の懸念点や確認事項を面接準備へつなげる

ことを目的とする。


# 61. 選考準備の基本構造

選考準備は、
以下の3階層で管理する。

1. 共通準備
2. 企業別準備
3. 選考別準備


## 61-1. 共通準備

複数企業で共通して使用できる、
利用者自身に関する準備内容を管理する。


## 61-2. 企業別準備

特定の応募企業・求人に対して、
企業や求人ごとに異なる準備内容を管理する。


## 61-3. 選考別準備

一次面接、二次面接、最終面接等、
個別の選考単位で必要な準備内容を管理する。

選考準備を単なる下書き保存機能にしない。
自分・企業・選考の3階層で整理する。
共通して使える内容を毎回ゼロから入力させない。
共通準備から企業別・選考別へコピーできるようにする。
コピー後はそれぞれ独立したデータとして編集できるようにする。
長文入力を考慮し、自動保存を基本とする。

選考終了後も準備内容を振り返れるようにする。
AIは回答を決定するのではなく、回答材料の整理を支援する。
AIマッチング結果を面接準備へ自然につなげる。
マイルストーンから該当する選考準備へ移動できるようにする。
利用者が自分の言葉で面接に臨めることを最優先とする。

# 81. 応募企業一覧の役割

応募企業一覧は、
応募後管理における現在の状況を一覧で把握するための機能とする。

マイルストーンが「これから何を、いつ行うか」を管理するのに対し、
応募企業一覧は、

「現在、各応募がどの選考段階にあるか」

を確認する役割を持つ。

応募企業一覧とマイルストーンは役割の異なる機能として管理するが、
利用者が現在地と次の予定を同時に確認できるよう、
応募管理画面内に統合して表示する。


# 82. 応募企業一覧の表示項目

応募企業一覧では、
以下を基本表示項目とする。

- 会社名
- 求人名
- 応募経路
- 現在フェーズ
- 次回予定
- 期限
- 対応状態
- 最終更新日時

会社名を応募詳細画面への主導線とする。

以下の詳細情報は一覧へ常時表示せず、
応募詳細画面で確認する。

- 面接URL
- 面接担当者
- 持ち物
- 詳細メモ
- 過去の活動履歴
- 選考準備本文


# 83. 応募企業一覧の初期表示対象

応募企業一覧では、
進行中の応募を初期表示対象とする。

以下の終了済み応募は、
通常の初期一覧から除外する。

- 不合格
- 辞退
- 見送り
- 選考不要
- 選考終了

終了済み応募のデータは削除しない。

利用者が、

「終了した応募も表示」

を選択した場合に確認できるようにする。


# 84. 応募企業一覧の並び替え

応募企業一覧では、
少なくとも以下の並び替えを提供する。

- 対応が必要な順
- 次回予定が近い順
- 最終更新が新しい順
- 最終更新が古い順
- 会社名順
- 現在フェーズ順

初期表示では、

1. 対応が必要
2. 近日予定
3. その他

を優先し、
同一グループ内では次回予定が近いものを優先する。

応募管理画面は、
単なる記録一覧ではなく、

「次に何をする必要があるか」

を把握することを優先する。


# 85. 応募企業一覧の検索・絞り込み

応募企業一覧では、
以下を基本的な検索・絞り込み項目とする。

- 応募経路
- 対応状態

- 適性検査
- 面接

- 内定
- 保留
- 終了

- すべて
- 対応が必要
- 近日予定
- 通常


# 86. 応募管理画面のサマリー

応募管理画面上部では、

基本表示は以下とする。

- 選考中
- 近日予定
- 対応が必要
- 内定

# 87. 応募管理画面の基本表示順

応募管理画面は、
以下の順序を基本とする。

1. 応募状況サマリー
2. 対応が必要
3. 直近のマイルストーン
4. 検索・絞り込み・並び替え
5. 応募企業一覧

「対応が必要」は、

通常のマイルストーンよりも優先して表示する。


# 88. 応募管理機能間の役割分担

応募後管理では、
各機能の役割を以下のように分離する。

## 応募企業一覧

「現在」を管理する。

主な問い：

「今、この応募はどの選考段階にいるか」


## マイルストーン

「未来」を管理する。

主な問い：

「次に、いつ、何をする必要があるか」


## 活動履歴

「過去」を管理する。

主な問い：

「これまでに何が起きたか」


## 選考準備

「未来の選考への準備」を管理する。

主な問い：

「次の選考に向けて何を準備するか」


# 89. 次のアクションとマイルストーンの区別

「次のアクション」と「マイルストーン」は別概念として扱う。

次のアクションは、

「今後行う必要があるが、まだ正式な予定・期限として登録していない行動候補」

とする。

マイルストーンは、

「日付または期限を持つ正式な予定」

とする。

例：

活動履歴
↓
次のアクション
「面接候補日を企業へ返信する」
↓
利用者が「マイルストーンに追加」
↓
8月20日
「面接候補日を返信」

次のアクションを入力しただけでは、
自動的にマイルストーンへ登録しない。


# 90. 応募後管理全体の役割構造

応募後管理全体は、
以下の役割構造を基本とする。

求人確認画面
↓
応募判断
↓
応募管理へ連携

応募管理
│
├─ 応募企業一覧
│   └─ 現在どこにいるか
│
├─ マイルストーン
│   └─ 次にいつ何をするか
│
├─ 活動履歴
│   └─ これまで何が起きたか
│
└─ 選考準備
    └─ 次の選考へ何を準備するか

各機能は相互に連携するが、
同じ情報を重複して管理しない。

画面上で同時に表示する場合でも、
内部データはそれぞれの役割に応じて分離する。


# 91. 応募管理画面と就職活動ダッシュボードの役割分担

応募管理画面は、

「現在の応募状況と次の行動を管理する画面」

とする。

初期実装の就職活動ダッシュボードは、

「就職活動全体を集計・分析する画面」

とする。

応募管理画面では、
詳細な分析指標を大量表示しない。

応募管理・活動履歴等で蓄積したデータを利用して、
初期実装で以下の分析を行う。

- 現在フェーズ集計
- 現在フェーズ内訳
- 応募数
- 書類通過数
- 書類通過率
- 面接進出数
- 内定数
- 応募経路別実績
- 選考に要した期間

応募管理画面とダッシュボードは、
同じデータを利用しても役割を分離する。

# 92. 応募詳細画面の役割

応募詳細画面は、
1件の応募について、

- 現在どの選考段階にいるか
- 今すぐ対応すべきことがあるか
- 次に何が予定されているか
- 次の選考に向けて何を準備するか
- これまで何が起きたか

を1画面で確認・管理するための画面とする。

応募企業一覧が複数応募を俯瞰する画面であるのに対し、
応募詳細画面は1件の応募について確認・操作する画面とする。


# 93. 応募詳細画面の表示順

応募詳細画面は、
以下の順序を基本とする。

1. 応募情報・現在地
2. 対応が必要
3. 次の予定・マイルストーン
4. 選考準備
5. 活動履歴

情報の優先順位は、

「現在地」
↓
「緊急対応」
↓
「次の予定」
↓
「次への準備」
↓
「過去」

とする。


# 94. 応募情報・現在地

応募詳細画面の最上部には、
現在の応募状況を常時表示する。

基本表示項目は以下とする。

- 会社名
- 求人名
- 応募経路
- 現在フェーズ
- 直近の選考結果
- 最終更新日時

利用者が画面を開いた時点で、

「どの求人について」
「現在どの段階にいるのか」

を把握できることを優先する。


## 94-1. 現在フェーズの更新

現在フェーズは、
選考結果やマイルストーンの操作による
自動遷移を基本とする。

例：

一次面接予定
↓
利用者が完了
↓
一次面接結果待ち
↓
一次面接通過
↓
次回選考の調整中

利用者が毎回現在フェーズを
手動選択する運用にはしない。

ただし、
企業独自の選考フローや例外的な状況へ対応するため、
現在フェーズを手動修正する手段は残す。


# 95. 対応が必要

未対応の重要事項が存在する場合は、
応募情報・現在地の直下に

「対応が必要」

を表示する。

対応が必要な項目がない場合は、
この領域自体を表示しない。


## 95-1. 表示内容

例：

一次面接  
予定日時：8月16日 14:00

予定日時を過ぎています。  
状況を更新してください。

操作例：

- 完了
- 延期
- 中止

延期を選択しても、
新しい予定が登録されていない場合は
「対応が必要」から解除しない。


# 96. 次の予定・マイルストーン

応募詳細画面では、
現在有効なActiveマイルストーンを常時表示する。

利用者が、

「次にいつ何をする必要があるか」

を確認する領域とする。


## 96-1. 基本操作

マイルストーンについて、
以下の操作を提供する。

- 新規登録
- 完了
- 延期
- 中止
- 日程変更
- 選考準備を開く


## 96-2. 過去のマイルストーン

Closedとなった、

- 完了
- 延期後に再調整済み
- 中止

等のマイルストーンは、
現在の予定一覧へ常時表示しない。

「過去の予定・履歴を見る」

等の折りたたみ領域から確認できるようにする。

過去情報を保持しながら、
現在対応すべき予定を見つけやすくする。


# 97. 選考準備

応募詳細画面では、
選考準備本文をすべて表示しない。

直近の選考に対応する準備状況と、
選考準備画面への導線を表示する。


## 97-1. 表示例

次回：

二次面接  
8月25日 14:00

準備状況：

- 想定質問：作成済み
- 逆質問：作成済み
- 確認事項：未作成

操作：

「二次面接の選考準備を開く」


## 97-2. 役割分担

応募詳細画面では、

「次の選考準備がどこまで進んでいるか」

を確認することを目的とする。

以下の詳細管理は、
選考準備画面側で行う。

- 共通準備
- 企業別準備
- 過去選考の準備
- 各テーマ本文の編集


# 98. 活動履歴

応募詳細画面の下部には、
最近の活動履歴を表示する。

活動履歴は、

「これまで何が起きたか」

を確認する領域とする。


## 98-1. 初期表示

初期状態では、
最近の主要な活動のみを表示する。

例：

8月17日  
二次面接の日程を登録

8月15日  
一次面接通過

8月14日  
一次面接を完了

操作：

- すべての活動を見る
- 活動を追加


## 98-2. 全履歴

「すべての活動を見る」

を選択した場合は、
自動記録と手動記録を含む
時系列タイムラインを表示する。

過去の詳細履歴を最初から大量表示せず、
必要な場合のみ確認できる構成とする。


# 99. 応募詳細画面の情報量制御

応募詳細画面は複数機能を統合するが、
すべての情報を最初から展開しない。

常時表示：

- 応募情報・現在地
- Activeマイルストーン
- 直近選考の準備状況
- 最近の活動

該当時のみ表示：

- 対応が必要

必要に応じて展開：

- 過去のマイルストーン
- 活動履歴の全件

別画面で管理：

- 選考準備本文

これにより、
1画面で応募状況を把握できる利点を維持しながら、
情報過多を防ぐ。


# 100. 応募詳細画面の役割分担

応募詳細画面内では、
以下の役割を混同しない。

## 応募情報・現在地

今どこにいるか。

## 対応が必要

今すぐ処理すべきことは何か。

## マイルストーン

次にいつ何をするか。

## 選考準備

次の選考へ何を準備するか。

## 活動履歴

これまで何が起きたか。


# 101. 応募詳細画面の設計原則

1. 1件の応募に必要な情報を1画面で把握できるようにする。
2. 現在地を画面最上部で明確にする。
3. 対応が必要な項目を通常情報より優先する。
4. 次の予定を過去の予定より優先する。
5. 過去の予定を削除せず、通常表示から分離する。
6. 選考準備本文を応募詳細へ詰め込まない。
7. 直近選考の準備状況だけ応募詳細で確認できるようにする。
8. 活動履歴は最近の情報を優先し、全履歴は必要時に展開する。
9. ステータスの自動遷移を基本とし、例外時の手動修正手段を残す。
10. 「現在 → 対応 → 予定 → 準備 → 過去」の順序を基本とする。

# 102. 応募企業一覧とWBSの統合

応募管理画面では、
応募企業一覧とマイルストーンのWBS表示を別画面へ分離せず、
同一の一覧内に統合する。

左側に応募企業の管理情報、
右側に選考スケジュールの時間軸を配置する。

基本構造：

応募企業一覧＋WBS
│
├─ 会社名
├─ 求人名
├─ 現在フェーズ
├─ 応募経路
├─ 次の予定・期限
├─ 対応状態
└─ WBS
     ├─ 予定
     └─ 実績

これにより利用者は、

「現在どの選考段階にいるか」

と、

「これまで・これから選考がどのように進むか」

を同一画面上で確認できるようにする。


# 103. WBSの役割

WBSは、

「複数企業の主要な選考スケジュールと、その前後関係を時間軸で把握する」

ための表示とする。

活動履歴のすべてをWBSへ表示する機能とはしない。

応募企業一覧が「現在地」を管理するのに対し、
WBSは「選考スケジュールの流れ」を視覚化する役割を持つ。


# 104. WBSの表示対象

WBSには、
選考進行に関係する主要なイベントを表示する。

基本表示対象は以下とする。

- 応募
- 書類提出
- 書類選考
- 適性検査
- カジュアル面談
- 一次面接
- 二次面接
- 最終面接
- その他の主要な面接・選考
- オファー面談
- 条件面談
- 企業への主要な回答期限
- 内定承諾期限
- その他、選考進行上重要な期限


# 105. WBSへ表示しない活動

以下のような細かなコミュニケーション活動は、
原則としてWBSへ表示しない。

- 企業へのメール
- 企業への電話
- 企業からの連絡
- エージェントへの連絡
- エージェントからの連絡
- エージェント面談
- お礼連絡
- 追加質問
- 情報収集

これらは活動履歴で管理する。

WBSへすべての活動を表示して情報量が過剰になることを防ぐ。


# 106. WBSの予定と実績

WBSでは、
主要な選考イベントについて、

- 予定
- 実績

の両方を表示する。

予定はマイルストーンを基礎とし、
実績は完了したマイルストーンおよび選考実施記録を基礎とする。

予定と実績は内部データとして混同せず、
UI上で同一時間軸に表示する。


## 106-1. 表示例

一次面接について、

予定：
8月20日

実績：
8月22日

であった場合、

当初予定と実際の実施日を
同一の時間軸上で確認できるようにする。

これにより、

- 予定どおり進行した
- 選考が前倒しになった
- 選考が後ろ倒しになった
- 日程変更が発生した

等を視覚的に把握できるようにする。


# 107. 延期・日程変更とWBS

日程変更時は、
既存仕様どおり旧予定を単純上書きしない。

旧予定：
延期として履歴保持

新予定：
新しいマイルストーンとして登録

とする。

WBSでは、
必要に応じて当初予定と変更後予定の関係を確認できるようにする。

ただし、
通常表示で過去の延期予定を大量表示して
視認性を損なわないようにする。

現在有効な予定を優先し、
過去予定の詳細は必要に応じて確認できる構造とする。


# 108. WBSの表示期間

WBSは、

- 週表示
- 月表示

を切り替え可能とする。


## 108-1. 週表示

直近の、

- 面接
- 適性検査
- 提出期限
- 回答期限

等を細かく確認する用途とする。


## 108-2. 月表示

複数企業の選考が、
一定期間の中でどのように進行しているかを
俯瞰する用途とする。


# 109. 応募企業一覧とWBSの表示構造

応募企業一覧の左側には、
以下を表示する。

- 会社名
- 求人名
- 現在フェーズ
- 応募経路
- 次の予定・期限
- 対応状態

右側には、
同じ応募に紐づくWBS時間軸を表示する。

概念例：

会社名
│ 求人名
│ 現在フェーズ
│ 応募経路
│ 次の予定・期限
│ 対応状態
│
└──────── WBS時間軸 ────────
          予定
          実績

会社名を応募詳細画面への主導線とする。


# 110. 「次の予定・期限」の統合表示

応募企業一覧では、

「次回予定」
と
「期限」

を別々の列として常時表示せず、

「次の予定・期限」

として統合して表示する。

例：

8/20　二次面接 14:00

または、

8/22　内定回答期限

内部データでは、
予定と期限を引き続き別の性質として管理する。

UI上では、

「利用者が次に意識すべき日時」

としてまとめて確認できるようにする。


# 111. WBSと他機能の役割分担

応募後管理では、
以下の役割分担を維持する。

## 応募企業一覧

現在地を確認する。

「今、この応募はどこにいるか」


## WBS

主要な選考スケジュールの流れを確認する。

「選考がいつ、どのように進むか」


## マイルストーン

個別の予定・期限を管理する。

「次にいつ何をするか」


## 活動履歴

細かなコミュニケーションを含め、
過去に起きた出来事を確認する。

「これまで何が起きたか」


## 選考準備

次の選考に必要な準備を行う。

「次に向けて何を準備するか」

WBSはマイルストーンや活動履歴を置き換える機能ではなく、
主要な選考進行を時間軸で可視化する表示機能として扱う。


# 112. 応募管理画面の更新後構成

応募管理画面は、
以下の構成を基本とする。

1. 応募状況サマリー
   - 選考中
   - 近日予定
   - 対応が必要
   - 内定

2. 対応が必要

3. 直近の予定
   - 直近1週間
   - 最大3件

4. 検索・絞り込み・並び替え

5. 応募企業一覧＋WBS
   - 応募企業の現在地
   - 次の予定・期限
   - 対応状態
   - 主要選考の予定
   - 主要選考の実績
   - 週／月表示切替


# 113. WBS設計原則

1. 応募企業一覧とWBSを同一画面で確認できるようにする。
2. WBS専用の独立画面は設けない。
3. WBSには主要な選考イベントだけを表示する。
4. 細かな連絡活動は活動履歴へ残す。
5. 予定と実績の両方を表示する。
6. 予定と実績の内部データは混同しない。
7. 週表示と月表示を切り替え可能にする。
8. 延期・日程変更の履歴を失わない。
9. 過去履歴を残しながら現在の予定を見やすくする。
10. WBSを「選考の前後関係を把握するための可視化」として位置付ける。

# 114. 就職活動ダッシュボードの位置付け

就職活動ダッシュボードは、
応募管理機能と同時に実装する主要画面とする。
初期実装の対象から除外せず、応募管理画面と同一リリースで提供する。

応募管理画面とダッシュボードは、
同じ応募・選考データを使用するが、
画面の役割を明確に分離する。

応募管理画面は、

「現在の応募状況を確認し、次の行動を管理する画面」

とする。

就職活動ダッシュボードは、

「就職活動全体の応募状況・選考実績を集計し、
活動全体を振り返る画面」

とする。


# 115. 応募管理画面とダッシュボードの役割分担

## 115-1. 応募管理画面

主な役割：

- 現在の応募状況を確認する
- 対応が必要な項目を確認する
- 直近の予定を確認する
- 応募企業ごとの現在フェーズを確認する
- マイルストーンを管理する
- WBSで選考スケジュールの流れを確認する

時間軸としては、

「現在～未来」

を中心に扱う。


## 115-2. 就職活動ダッシュボード

主な役割：

- 就職活動全体の状況を集計する
- 現在フェーズの分布を確認する
- 選考実績を確認する
- 書類通過率を確認する
- 面接進出状況を確認する
- 内定状況を確認する
- 応募経路ごとの成果を比較する

時間軸としては、

「これまでの活動～現在」

を集計・分析する。


# 116. 就職活動ダッシュボードの基本構成

就職活動ダッシュボードは、
以下の4領域を基本構成とする。

1. 就活状況サマリー
2. 現在フェーズ
3. 選考実績
4. 応募経路別実績


# 117. 就活状況サマリー

画面上部に、
就職活動全体を短時間で把握するための
サマリーカードを表示する。

基本表示項目は以下とする。

- 管理対象
- 応募
- 面接進出
- 内定

例：

管理対象：32社
応募：24社
面接進出：8社
内定：2社


## 117-1. 応募管理画面との違い

応募管理画面のサマリーは、

- 選考中
- 近日予定
- 対応が必要
- 内定

を表示する。

一方、
ダッシュボードでは、

- 管理対象
- 応募
- 面接進出
- 内定

を表示する。

応募管理画面は行動管理、
ダッシュボードは活動実績の把握を目的とする。


# 118. 現在フェーズ集計

現在フェーズでは、
各応募が現在どの選考段階に存在するかを集計する。

基本的な大分類は以下とする。

- 応募準備
- 書類選考
- 適性検査
- 面接
- オファー・条件確認
- 内定
- 保留
- その他・終了


# 119. 現在フェーズの表示形式

現在フェーズの集計は、
円グラフでは表示しない。

現在フェーズには選考進行上の順序が存在するため、
割合だけを表現する円グラフではなく、

「横棒グラフ」

を使用する。

表示例：

応募準備        ███             3社
書類選考        ████            4社
適性検査        █               1社
面接            ██████          6社
オファー・条件  █               1社
内定            ██              2社
保留            █               1社
その他・終了    ██████████████ 14社

件数と全体に占める割合を
同時に確認できる構成とする。


# 120. 詳細フェーズ内訳

現在フェーズの大分類とは別に、
詳細フェーズ内訳を表示する。

例：

- 書類選考中
- 適性検査予定
- 一次面接調整中
- 一次面接予定
- 一次面接結果待ち
- 二次面接調整中
- 二次面接予定
- 二次面接結果待ち
- 最終面接調整中
- 最終面接予定
- 最終面接結果待ち
- オファー面談予定
- 条件確認中

等。

詳細フェーズ内訳は、
グラフを主役とせず、
件数を確認しやすいリスト形式を基本とする。


# 121. 選考実績

選考実績では、
応募から内定までの選考進行を
全体に対する比率が視覚的に分かる形式で表示する。

基本的な流れは以下とする。

応募
↓
書類結果判明
↓
書類通過
↓
面接進出
↓
最終面接
↓
内定


# 122. 選考実績の表示形式

選考実績は、
単純な表形式を主表示にはしない。

各段階の件数と、
前段階または基準件数に対する割合を
視覚的に確認できるフロー／ファネル形式を使用する。

基本表示例：

応募
24社
↓
書類結果判明
18社
↓
書類通過
9社
↓
面接進出
8社
↓
最終面接
3社
↓
内定
2社

各段階には件数を明示する。


# 123. 選考実績の主要指標

選考実績には、
少なくとも以下を表示する。

- 書類結果判明数
- 書類通過数
- 書類通過率
- 面接進出数
- 面接進出率
- 最終面接進出数
- 内定数
- 内定率


# 124. 書類通過率

書類通過率は以下の式で算出する。

書類通過率
＝ 書類通過数
÷ 書類結果が判明した応募数
× 100

分母を応募総数にはしない。

書類選考中等、
まだ結果が判明していない応募を
不通過として扱わないためである。


# 125. 面接進出率

面接進出率は、
書類結果が判明した応募のうち、
面接フェーズへ進んだ応募の割合を基本とする。

面接進出数とあわせて表示し、
件数と率の両方を確認できるようにする。


# 126. 内定率

内定率は、
応募数を基準とした割合として表示する。

内定率
＝ 内定数
÷ 応募数
× 100

件数も併記する。


# 127. 応募経路別実績

応募経路別実績では、
利用者が実際に応募した経路ごとの成果を集計する。

紹介された経路ではなく、

「実際の応募経路」

を基準とする。

同一求人が複数経路から紹介されていた場合でも、
実際に応募した経路の実績として集計する。


# 128. 応募経路別実績の表示項目

応募経路ごとに、
少なくとも以下を表示する。

- 応募数
- 書類結果判明数
- 書類通過数
- 書類通過率
- 面接進出数
- 内定数

表示例：

| 応募経路 | 応募数 | 結果判明 | 書類通過 | 書類通過率 | 面接進出 | 内定 |
|---|---:|---:|---:|---:|---:|---:|
| リクルートエージェント | 10 | 8 | 4 | 50% | 3 | 1 |
| doda | 8 | 6 | 2 | 33% | 2 | 0 |
| 直接応募 | 5 | 5 | 3 | 60% | 2 | 1 |


# 129. 応募経路別書類通過率

応募経路ごとの書類通過率も表示する。

計算式は、
全体の書類通過率と同じく、

応募経路別書類通過率
＝ その応募経路の書類通過数
÷ その応募経路で書類結果が判明した応募数
× 100

とする。

応募数そのものを分母にはしない。


# 130. 応募経路別実績の表示形式

応募経路別実績は、

1. 詳細な件数を確認する表
2. 書類通過率を比較する横棒グラフ

を組み合わせて表示する。

表では正確な数値を確認し、
横棒グラフでは応募経路ごとの
書類通過率の差を視覚的に比較できるようにする。


# 131. 一般的な通過率との比較

初期実装では、
市場平均や一般的な書類通過率との比較は行わない。

外部の基準値を使用する場合、
対象職種、年代、応募経路、時期等によって
適切な比較基準が異なるためである。

初期実装では、
利用者自身の実績値を正確に表示することを優先する。


# 132. ダッシュボードの集計期間

初期実装では、
全期間の応募活動を集計対象とする。

将来的な期間フィルター追加を妨げない構造とするが、
初期実装では期間指定機能を必須としない。

将来追加する場合の候補：

- 全期間
- 直近30日
- 直近3か月
- 任意期間


# 133. ダッシュボードUIの基本デザイン

ダッシュボードは、
既存のMeTeA画面デザインと統一する。

基本方針：

- 白～薄い青灰色の背景
- 白背景のカード
- 薄い境界線
- 適度な角丸
- MeTeAの既存ブルーを主要色として使用
- 強調しすぎない補助色
- 見出し、本文、補足情報の文字階層を既存画面へ合わせる
- 色だけに意味を依存しない

分析専用SaaSのように
大量のグラフを並べるのではなく、

「利用者が自分の就職活動を理解できること」

を優先する。

# 137. 最終設計原則

1. ダッシュボードと応募管理を混同しない。
2. ダッシュボードは集計・分析に特化する。
3. 応募管理は現在の状況と次の行動の管理に特化する。
4. WBSは応募企業一覧と同一画面に表示する。
5. WBSには主要な選考イベントのみ表示する。
6. WBSでは予定と実績を確認できるようにする。
7. 細かなコミュニケーションは活動履歴で管理する。
8. 現在フェーズは円グラフではなく横棒グラフで表示する。
9. 選考実績は全体に対する進行状況が分かる図表で表示する。
10. 応募経路別の書類通過率を確認できるようにする。
11. 書類通過率の分母には結果判明数を使用する。
12. 既存のMeTeA UIデザインを全画面で統一する。
13. データを重複管理せず、同じデータを目的に応じて異なる粒度で表示する。
14. 利用者が「現在・未来・過去・準備・全体分析」を迷わず行き来できる構造とする。

# 138. 実装確定事項（2026-08-17）

## 138-1. マイルストーン状態

マイルストーンは次の4状態で管理する。

- 未完了（pending）
- 完了（completed）
- 延期（postponed）
- 中止（cancelled）

延期時は元の予定を延期として保持し、変更後の日付で新しい予定を作成する。
新しい予定は `rescheduled_from_id` により元の予定と関連付ける。
中止時も予定を削除せず、理由と中止日時を履歴として保持する。

## 138-2. 期限・近日予定の判定

- 未完了かつ予定日・期限が当日以前：対応が必要
- 未完了かつ当日より後、7日以内：近日予定
- 当日は「対応が必要」にのみ含め、近日予定とは重複させない
- 完了・延期・中止は期限判定の対象外

## 138-3. 活動履歴

以下を自動記録する。

- 応募管理への追加・同期
- 選考フェーズ・結果の変更
- マイルストーンの登録・完了・延期・中止

利用者は連絡やメモなどの活動を手動でも追加できる。

## 138-4. 初期実装範囲

初期実装には応募管理画面だけでなく、就職活動ダッシュボードも含める。
ダッシュボードでは管理対象数、応募数、面接進出数、内定数、現在フェーズ、選考実績、応募経路別実績を確認できる。

# 応募管理サマリーカードの確定仕様（2026-08-17）

応募管理画面上部の4カードは、選考結果の実績ではなく、利用者が今対応すべき対象を把握するための運用サマリーとする。

| カード | 集計対象 | 単位 |
|---|---|---|
| 応募準備 | 「応募する」と判断済みで、応募・書類提出前の企業 | 社 |
| 選考中 | 応募・書類提出後から選考終了前までの企業（応募準備・内定・終了を除く） | 社 |
| 近日予定 | 今日より後、7日以内に予定されている未完了タスク | 件 |
| 対応が必要 | 期限当日または期限超過となった未完了タスク | 件 |

カードを押すと、その分類に該当する企業だけを応募企業一覧に表示する。近日予定・対応が必要のカード数はタスク件数だが、一覧では該当タスクを持つ企業を重複なく表示する。

「内定」は日々の対応対象を示す運用カードから外し、就職活動ダッシュボードの実績・フェーズ集計で確認する。

この節の定義は、同一文書内にある過去の応募管理サマリー定義より優先する。

### 139-9. 準備率と完了判定

準備率は、現在の選考で必要なテーマのうち、完了したテーマの割合として算出する。

準備率 ＝ 完了した対象テーマ数 ÷ 対象テーマ数 × 100

対象外のテーマは、準備率の分母に含めない。

テーマの完了判定には、次の2方式を使用できる。

- 必要な入力が完了したことによる自動判定
- 利用者が「完了」として確認するチェック方式

自動判定だけでは内容の十分性を判断できない場合があるため、利用者による完了確認を併用できるものとする。

### 139-10. AI支援の役割

AIは、利用者に代わって面接回答の完成文を作成する機能ではない。

AIの役割は、利用者が自分で回答を考え、整理するための材料を提示することである。

AIが提示できる内容の例は、次のとおり。

- 利用者の職務経歴から活用できる経験
- 求人票と利用者情報の接続点
- 企業研究で確認すべき観点
- 回答を具体化するための問い
- 不足している情報
- 矛盾や確認が必要な情報

AIが提示した内容は、そのまま確定回答として保存しない。

利用者が内容を確認し、自分の言葉で編集・整理したうえで保存することを前提とする。

### 139-11. 面接後の振り返り

面接後は、次の情報を記録できるようにする。

- 実際に聞かれた質問
- 自分の回答
- 回答の自己評価
- 面接官の反応
- 次回へ向けた改善点
- 補足メモ

記録した内容は、次回以降の選考準備に利用する。

振り返り情報は応募企業および選考単位で管理し、過去の面接内容と次回の準備内容を関連付けて確認できるようにする。

各画面の役割は、次のとおりとする。

#### 就職活動ダッシュボード

- 管理対象の企業数

- 書類通過率
- 面接進出率
- 内定率

#### 応募管理・WBS

複数企業の予定、期限および選考進捗を横断して管理する画面とする。

主に次の情報を表示する。

- 対応が必要な予定
- 直近の予定
- 応募企業一覧

#### 応募詳細

### 139-14. データ保存の基本方針

応募後管理で入力・更新された情報は、SQLiteへ保存する。

保存対象には、少なくとも次の情報を含める。

- 応募企業
- 現在フェーズ
- 応募経路
- 選考予定
- 期限
- 対応状態
- 活動履歴
- 選考準備テーマ
- テーマの入力内容
- テーマの完了状態
- 準備率
- 面接後の振り返り
- 補足メモ

予定、活動履歴および振り返りは、対象となる応募企業と関連付けて保存する。

選考準備は、応募企業および選考単位で管理する。

### 139-15. UX上の基本方針

応募後管理では、利用者が次に行うべきことを迷わない構成を優先する。

そのため、画面では次の順序で情報を提示する。

1. 対応が必要な項目
2. 直近の予定・期限
3. 現在の選考状況
4. 選考準備の進捗
5. 過去の活動履歴
6. 分析・振り返り情報

対応が必要な項目が0件の場合は、警告カードを表示しない。

期限超過や早急な対応が必要な項目は赤色系、期限が近い項目はオレンジ色系、完了済みの項目は緑色系で識別する。

通常の操作および主要ボタンには、MeTeA共通の青色を使用する。
