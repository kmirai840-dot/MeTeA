# 保存・遷移の速度改善

更新日：2026年9月13日

## As-Is / To-Be

| 対象 | As-Is | To-Be |
|---|---|---|
| 「次へ」受付 | 旧入力画面を描画してからボタンを処理 | 基本情報・希望条件・価値観・就活の軸はコールバックで保存要求だけ記録し、描画前に保存。成功後に遷移。検証エラーはそのまま入力画面を描画。職歴は既存の保存コールバックを維持 |
| DB接続 | 保存前読込・正式保存・活動履歴・AI評価の失効処理で別接続・別コミット | サービス操作内で1接続を共有。正式保存・活動履歴・AI評価失効は一括コミット。途中失敗は一括ロールバック |
| 保存前の下書き | 独立して永続保存 | 維持。正式保存に失敗しても下書きが残る |
| 有効性チェック | 各Repositoryが同じ操作中に何度もDB確認 | 同一操作・同一本人・同一招待設定では一回だけ。次の操作では必ず再確認。IDと親所有者の一致確認は省略しない |
| 価値観・軸の行登録 | 各回答を1件ずつ送信 | 必要な採番IDを使わない登録をexecutemanyへ集約。PostgreSQLはpsycopgの一括送信を使用 |
| 再遷移時のGoogle認証 | 毎回DB初期化確認・登録ロック・メール重複確認・最終ログイン更新 | 検証済み本人情報がセッションと一致すれば、DBで有効性・Google subject・招待対象を確認。初回／本人情報変更／セッション再確立は従来の登録確認を実行 |

UIの入力部品・配置・ボタン名は変更しない。保存を裏で走らせたまま次画面へ進む処理は追加しない。

## 実装と保護

- `database/operation.py`：ContextVarで操作を隔離。Repositoryのcommit/closeを外側へ委譲し、最外側で必ず終了・リセットする。ネストした処理の例外やrollbackが捕捉された場合も、外側のコミットを禁止する。
- `database/access_control.py`：本人と指定IDの一致は毎回確認。有効性確認の再利用は操作の寿命だけで、グローバルキャッシュや時間ベースの省略ではない。
- `services/google_auth_service.py`：Google issuer/subject/email/email_verified/name/pictureの変化で再解決。未ログイン・停止・削除・招待解除は従来通り拒否。再確認ではsubjectの一致もチェック。一時接続失敗で本人IDが停止されている場合は通常解決へ戻る。last_login_atは画面ごとではなく登録確認時に更新する。
- `ui/page_execution.py`：保存要求はサーバーセッション内に保持し、一度だけ取り出す。基本情報は従来の送信時入力スナップショットを維持。失敗メッセージは従来の保存ボタン付近に表示する。

## 計測結果と限界

実利用者データを変更せず、同じNeon DB内に専用の一時スキーマを作り、合成データで計測した。計測用スキーマは終了後に削除した。

| 対象（サービス処理のみ） | 変更前・2回 | 改善後・2回 |
|---|---|---|
| 基本情報の正式保存 | 6.767秒 / 4.347秒 | 0.918秒 / 0.902秒 |
| 価値観の正式保存 | 7.495秒 / 4.205秒 | 1.552秒 / 1.357秒 |
| 就活の軸候補の読込 | 2.922秒 / 5.729秒 | 0.903秒 / 0.911秒 |

別の準備実行では価値観保存が2.769秒となり、通信条件による変動を確認した。上記はクリックから画面表示までの時間ではない。

ローカルStreamlit＋ヘッドレスEdge＋Neon専用テストスキーマで、保存前再描画を除去した後のクリックから次画面の見出し表示までは、基本情報3.086秒、価値観4.151秒。ブラウザ側のscript-stateがnotRunningになるまでは、それぞれ3.491秒・7.415秒だった。Googleの検証済みセッションはテスト用情報で代替し、DB有効性確認と画面・保存処理は実コードを使用。Cloud本番・実端末の同条件計測ではない。

**「通常1秒・最長3秒以内」という画面遷移全体の目標は未達。** サービス保存時間の短縮と、画面全体の3秒達成を混同しない。通信・休止復帰・初回描画を含めた全ケースの上限も保証しない。公開環境での再測定と、画面描画側の待ち時間の調査を継続課題とする。

## 検証

回帰テストに加え、正式保存後の副処理失敗でプロフィールと下書き削除を巻き戻すこと、捕捉されたrollback・ネスト例外でもコミットしないこと、接続を1回だけ取得すること、別人IDを拒否すること、次の操作で有効性を再確認すること、認証本人の変更・停止を検出すること、4画面の一回押下で旧画面を描画せず保存・遷移することを検証した。入力エラー時の最新入力保持も確認対象とする。

一括送信の根拠：[psycopg pipeline/executemany公式仕様](https://www.psycopg.org/psycopg3/docs/advanced/pipeline.html)。

## 2026-09-13 求人一覧から詳細への待ち時間改善

As-Is：詳細画面の求人・評価・基本情報・通勤時間・確認状態・応募判断を個別接続で取得し、各Repositoryで認証状態の確認が重複していた。To-Be：初期取得だけdatabase_operationで接続・アカウント確認を共有し、取得済みデータを各描画へ渡す。描画と保存ボタン処理はトランザクション外とし、再実行で保存が巻き戻らない構成。全利用者共通のキャッシュは作らず、所有者確認を維持する。処理中は保存済み情報の読込表示を出す。

公開DBを使うローカル読取計測では、同じ6種類の取得が個別6.86秒→共有1.27秒。これはDB読取部分の計測であり、20秒停止の全要因の特定や全画面3秒保証ではない。1接続での取得、描画前の終了、取得済み評価の再利用、各描画への引き渡しをテスト。



## 2026-09-13：入力処理・評価整合性の更新

入力中の再実行をフォーム化で削減。数値条件の更新はAI再試行を待たず保存済み意味判定と合成する。全操作の1〜3秒以内を保証する計測結果ではない。
