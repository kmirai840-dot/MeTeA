対象コード：92de66f。調査のみ。アプリのロジック・UI・公開設定は変更しない。

## 調査範囲と証拠の区別

app.pyの全ルートと、入力・確認・比較・応募・運営者の呼出し先を静的調査。全画面のブラウザ操作時間を測ったものではない。AI実行、保存、初回テンプレート作成は実データを変更するため再実行しない。応募同期を含む読取計測にはSELECT以外を拒否する監視を付け、全ケースで書込みは発生しなかった。コード上の処理の存在と、その処理が占める秒数は区別する。

## 共通する要因

- 通常遷移はGoogle OAuthを毎回実行しないが、検証済み本人が有効かDB確認する。その後、各独立したDB操作でも有効性を確認。安全性を保ったまま同一操作内の重複を減らす余地がある。
- 接続プールは既に存在（最大6）。「プールを追加するだけ」は新しい改善にならない。取得ごとのヘルスチェック・トランザクション設定・返却もあるため、問い合わせ数だけでなく接続取得数が効く。
- 通常の折りたたみは閉じていても中身を計算・送信する。MeTeAの求人詳細も該当する。
- 希望条件等の表示制御は100ミリ秒間隔でDOM検索。入力時にサーバー通信しないための処理であり、これ自体はDB再読み込みではない。端末CPUへの実際の影響は未計測。
- 評価済み・変更なしの求人を開くたびにAI実行する設計ではない。変更・待機状態の評価はバックグラウンド実行（同時2件）と3秒間隔の結果確認があり、完了時に表示が更新される。待機中はDB通信と競合する可能性があるが、今回負荷試験は未実施。
- AI評価の1リクエストには75秒のタイムアウト設定がある。実際に毎回75秒かかる意味ではない。求人・職歴抽出のコードには同様の明示タイムアウト指定がない。精度を落とすモデル変更を速度改善の前提にしない。

## 方法のメリット・デメリット

| 方法 | メリット | デメリット・注意 | 適用判断 |
|---|---|---|---|
| 一括取得・重複排除 | UIと精度を変えず通信往復を削減 | 所有者確認・更新後の読直しの検証が必要 | 最優先 |
| 必要な求人・列・件数のみ取得 | 転送量・変換・描画が減る | 絞り込み・並び順・集計との整合性確認が必要 | 詳細・比較・確認画面に有効 |
| 表示時の同期・初期作成を分離 | 画面表示がデータ更新待ちにならない | 保存側への移設、既存データの補完、失敗復旧が必要 | 応募関連に有効 |
| 非表示部分の遅延描画・局所更新 | 初期表示を軽くし、入力場所を維持 | 初めて開く際に待ちが移る。全体再実行を戻さない設計が必要 | 描画負荷計測後 |
| DOM監視を変更時だけ実行 | スマホ等のCPU負担を抑えられる可能性 | 部品構造依存、開閉・入力保持のブラウザ検証が必要 | 希望条件・求人入力 |
| AI処理をバックグラウンド化 | 画面の操作待ちを減らしモデル精度を維持 | AI完了自体は速くならない。再起動・重複実行・失敗管理が必要 | 文書抽出に検討 |
| 長時間キャッシュ | 再訪時の読み込みを減らせる | 古い値・別人データ混入の危険。変更検知設計が必要 | 一律適用しない |
| 配置地域統一・常時稼働 | 通信や休止復帰の待ちを減らせる | 費用・移行・設定変更が必要。現環境の地域と休止設定未確認 | 今回の①で残る場合の候補 |
| React等＋Python API | 画面を保持して必要箇所だけ更新しやすい | 工数・認証・保存・全画面の再検証が必要 | ③としてリリース後 |

DB索引の追加は現DBの実行計画を確認してから判断する。少人数・少件数で通信往復が支配的な場合、索引だけでは効かない。並列化も接続最大数・所有権・一貫性・AI同時処理を確認してから行う。

## 推奨順

1. 求人詳細・比較・登録内容確認の重複取得を減らす（UI変更なし）。
2. 応募管理・レポートの表示時同期、選考準備の初期作成を整理。
3. 希望条件・求人入力の描画時間を端末上で測り、必要な部分だけ改善。
4. 運営者の全表二重取得と先行ZIP作成を分離。
